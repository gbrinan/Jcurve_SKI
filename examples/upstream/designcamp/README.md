# 디자인캠프 산출물 — Activity Coach의 상류 입력

세션 3~6 파이프라인에서 **가장 앞단**에 오는 문서들입니다.

```
디자인캠프 산출물(이 폴더)  →  사람 수정  →  와이어프레임 코치  →  스킬 제작  →  Activity Coach
```

## 왜 이 폴더가 필요한가

원본 업무에는 **분기(◆)와 루프백(↩)이 있습니다.** 그런데 와이어프레임 단계에서
그 정보가 사라집니다 — 참가자는 각자 자기 Lv6 하나만 그리기 때문입니다.

디자인캠프 문서의 `Process Flow` 절이 그 정보를 갖고 있는 **유일한 자리**입니다.
Activity Coach는 여기서 분기와 루프백을 읽어옵니다.

## 문서 형식 (Agent 4 — To-Be Designer v1.2)

회계관리팀 원본의 절 구성을 그대로 따릅니다.

| 절 | 내용 | Activity Coach가 쓰는가 |
|---|---|---|
| 1. 개요 | 참가자·시스템·규모 | 출처 표기 |
| 2. 업무 Level 정의 | Lv1~Lv6 이름과 ID 접두사 | **레벨 대응에 필수** |
| 3. As-Is Task Tree | `P-` / `T-` / `A-` 계층 | Lv5·Lv6 후보 |
| 4. Pain Point & AX 매핑 | PP 목록·유형 분포·AX화 추천 | 스킬 본문의 근거 |
| 5. As-Is Process Flow | **텍스트 흐름도 (◆ 분기 · ↩ 루프백 · [HITL])** | **분기·루프백의 출처** |
| 6. To-Be 최적화 계획 | ECRS · OPT 액션 | Human 여부(자동/증강/사람고유) |
| 7~8. To-Be Task Tree / Flow | `[🤖]` `[HITL]` `[🤖+HITL]` 표기 | **여기서 팩을 만든다** |
| 9~10. 비교 · 변화 관리 | 정량 비교, 선행 조건 | 데이터 명세 인터뷰 준비 |
| 11. 후속 모듈 연계 가이드 | **Activity Coach 인계 사항** | 패키징 단위·갈림길·루프백 |

### 표기 대응

| 원본 표기 | 우리 `human` 필드 |
|---|---|
| `[🤖]` | 자동 |
| `[🤖+HITL]` | 증강 |
| `[HITL]` | 사람고유 |
| (표기 없음) | 증강 (기본) |

### 레벨 대응

원본 Agent 1은 Lv5를 「Activity」로, Agent 3·4는 Lv6을 「Activity」로 부릅니다.
**Agent 3·4 기준이 정본**이며, 우리 도구와는 이렇게 대응합니다.

| 원본 (Agent 3·4) | 우리 |
|---|---|
| Lv3 업무 | Lv4 |
| Lv4 프로세스 `P-` | **Lv5** ← 패키징 단위 |
| Lv5 Task `T-` | **Lv6** ← 스킬 하나씩 |
| Lv6 Activity `A-` | 스킬 본문의 판단기준 |

## 여기서 팩까지 가는 길

각 문서 11절의 **Activity Coach 인계 사항**을 설계도 HTML로 옮긴 뒤 변환합니다.

```bash
# 1) 설계도 (인계 사항을 그대로 옮긴 것 — examples/upstream/workflow/ 에 있음)
# 2) 변환
python3 check/adapt_workflow.py examples/upstream/workflow/성과평가운영-설계도.html /tmp/pack
# 3) 판정
python3 check/run_check.py /tmp/pack
python3 check/readchk.py  /tmp/pack
```

네 조직 모두 **팀 에이전트**로 나옵니다.

| 조직 | Lv5 (패키징 단위) | 갈림길 | 루프백 | 판정 |
|---|---|---|---|---|
| 재무본부 회계관리팀 | 분기/반기 결산 | 2갈래 | 차이분석조정 ↩ 계정검증대사 | 팀 에이전트 |
| Talent AX실 인사운영팀 | 연간 성과평가 운영 | 2갈래 | 이상조직조정요청 ↩ 리더평가입력점검 | 팀 에이전트 |
| 성과관리실 전략기획팀 | 월간 실적 마감 및 경영보고 | 2갈래 | 소명요청검토 ↩ 편차분석 | 팀 에이전트 |
| 전사 운영혁신팀 | 개선과제 발굴 및 심의 | **3갈래** | 보완요청 ↩ 효과정량화 | 팀 에이전트 |

## 네 문서를 나란히 놓고 보이는 것

**네 팀 모두 `DEC`(판단편차) Pain Point를 갖고 있습니다.**

| 팀 | DEC Pain Point |
|---|---|
| 회계관리팀 | (해당 유형 없음 — RPT·MAN·WAIT 중심) |
| 인사운영팀 | PP-5 평가 편차 조정 기준 불명확 · PP-11 노무 사안 등급 판정 편차 |
| 전략기획팀 | PP-5 편차 임계값 기준 사업부마다 다름 |
| 운영혁신팀 | PP-2 심사 등급 판정 기준 심사자별 편차 · PP-10 인정/불인정 기준 모호 |

그리고 세 팀 모두 같은 결론에 닿습니다 — **판정 기준을 명문화하는 것이 AX화의 선행 조건**입니다.
지금은 담당자 경험에 있고, 그래서 자동 판정이 불가능합니다.
이것이 세션 4 Wireframe Coach의 「3단 파고들기」가 겨냥하는 지점입니다.

또 하나: **갈림길은 대부분 사람이 판단하는 자리이고, 그 뒤에 루프백이 붙습니다.**
판단 → 되돌려보냄 → 다시 판단. 네 팀의 흐름이 전부 이 모양입니다.
