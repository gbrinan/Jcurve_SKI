# 통합 패키징 테스트 통합 점검기 (Lv.5 Integration Harness)

**목적**: 개인 Lv.6 스킬들이 하나의 팀 Lv.5 에이전트로 "잘" 통합되었는지 판정한다.

**성공 조건** (사용자 정의 그대로):
> 기존 스킬의 맥락이 충분히 반영되면서도, 맥락 충돌과 일관성이 깨지지 않고,
> 하나의 일을 처음부터 끝까지 위임할 수 있는 에이전트로 통합되어야 한다.

이를 4개 검증 레이어로 분해한다. L1~L3은 스크립트(`run_check.py`)가 기계적으로 판정하고,
L4의 일부는 사람(또는 AI 리뷰어)이 시나리오를 실제 실행해 판정한다.

## 검증 레이어

### L1. 구조 (패키징이 규격을 지키는가)
- [ ] 필수 파일 존재: README.md, agent-plan.md, AGENTS.md, skills/, data/
- [ ] 각 skill.md에 기계가 읽을 헤더(frontmatter)가 있는가: name, inputs, outputs, reads, writes, next
- [ ] agent-plan.md가 팩 안에 하나만 존재하는가 (SSOT 유일성)

### L2. 맥락 반영 (기존 스킬의 맥락이 살아있는가)
- [ ] 모든 스킬이 agent-plan.md에 언급되는가 (기획서가 모르는 스킬 = 반영 안 된 맥락)
- [ ] 각 스킬이 읽고/쓰는 표가 전부 기획서 3절 데이터 명세에 있는가 (명세 밖 데이터 = 누락된 맥락)
- [ ] 스킬 본문이 비어있지 않은가 (헤더만 있는 스킬 = 맥락 소실)

### L3. 맥락 충돌·일관성 (합쳤을 때 서로 싸우지 않는가)
- [ ] **단일 기록자**: 같은 표에 쓰는(writes) 스킬이 2개 이상이면 실패 — 기록 주체는 표당 하나
- [ ] **흐름 정합**: 시작점 1개, 모든 스킬에 도달(고아 없음), 순환 없음, next가 실재하는
      스킬을 가리키는가, 앞 스킬의 outputs와 뒤 스킬의 inputs가 이름까지 일치하는가
      (갈림길은 허용한다 — 위 '산출물 유형' 참조)
- [ ] **용어 일관**: 표 이름 문자열이 파일마다 다르게 쓰이지 않는가 (예: 견적비교표 vs 견적_비교표)
- [ ] **규칙 일관**: 휴먼인더루프 임계값(예: ±15%)이 AGENTS.md·기획서·스킬에서 같은 값인가

### L4. 처음부터 끝까지 위임 (End-to-End)
- [ ] 체인의 시작 입력 = 기획서 4절 시나리오의 입력, 체인의 끝 출력 = 시나리오의 산출물
- [ ] 마지막 단계가 자동 발송하지 않고 휴먼인더루프에서 멈추는가 (기계 판정: 최종 스킬 writes 없음 + 확인 요청 명시)
- [ ] **[사람 판정]** 시나리오를 실제로 한 번 실행: 트리거부터 산출물까지 사람 개입이
      선언된 휴먼인더루프 지점 외에 없었는가
- [ ] **[사람 판정]** 틀린 입력(미승인 공급사, ±15% 초과 단가)을 넣었을 때 실제로 멈추는가

## L0 — 계약 준수 게이트 (통합 점검기보다 먼저)

팀원이 **각자 자유롭게 만들어 온** 스킬은 표 이름·페이로드 이름·임계값이 서로 어긋난다.
그 상태로 점검기를 돌리면 실패가 쏟아질 뿐 아니라, **이름이 어긋난 탓에 진짜 충돌이 가려진다.**

실측 예: 두 사람이 같은 표에 기록하는데 한 명은 `견적비교표.xlsx`, 다른 명은 `견적_비교표.xlsx`로
적으면 통합 점검기의 단일 기록자 검사가 서로 다른 표로 보고 **통과시킨다**. 임계값도 한 명이 "20% 넘게",
다른 명이 "±15%"로 적으면 형식이 달라 검사에 걸리지 않는다.

그래서 점검기 앞에 계약 준수 게이트를 둔다. 게이트가 정본 이름을 보장하므로,
점검기는 "이름은 이미 맞다"는 전제 위에서 구조와 일관성만 보면 된다.

```
python3 check/check_contract.py <팩 경로> [--run-check]
```

`CONTRACT.md`의 ```contract 블록(표·기록자·체인·페이로드·임계값·정지 지점)과 대조해 세 갈래로 분기한다.

| 판정 | 뜻 | 처리 |
|---|---|---|
| 🟢 GREEN (0) | 위반 없음 | `--run-check`를 주면 곧바로 통합 점검기 실행 |
| 🟡 YELLOW (1) | 표기 변형뿐 (`견적_비교표` vs `견적비교표`) | `REMEDIATION.md`에 치환 제안 → 사람이 확인·반영 후 재검사 |
| 🔴 RED (2) | 팀 결정이 필요 (기록자 중복, 계약에 없는 표·이름, 임계값 상충, 체인 밖 스킬) | 자동 교정하지 않음. 팀이 계약이나 담당을 정하고 재검사 |

RED가 하나라도 있으면 YELLOW 교정안을 만들지 않는다 — 이름부터 고쳐도 소용없기 때문(제거 우선).

## 정지 지점(halt_at) — 체인 중간도 선언할 수 있다

실측(워크플로우 설계도 변환 테스트)으로 확인된 문제: 사람고유 판단이 체인 **중간**에
있을 때, 그 지점의 확인·정지 문구가 통째로 빠져도 통합 점검기가 전체 통과를 냈다.
L4는 체인의 **끝점만** 검사하기 때문이다.

`halt_at`에 콤마로 여러 스킬을 적으면 계약 게이트(L0)가 전부 검사한다:

```
halt_at: 중간판단스킬, 끝스킬
```

체인 중간에 사람고유 판단이 있으면 반드시 halt_at에 추가한다. 끝점만으로는
중간 지점의 문구 누락을 잡지 못한다는 것이 실측으로 확인됐다.

## 갈림길(when)과 루프백(loop_to) — 원본 업무의 흐름을 그대로 받는다

원본(디자인캠프 Process Flow)에는 분기(◆)와 루프백(↩)이 실제로 있다 — 반려·재작업·재대사.
와이어프레임 단계에서 이 정보가 죽는다(참가자는 각자 자기 LV6 하나만 그린다). 그래서:

- **갈림길**: `next: A | B` 로 적고, 어느 쪽으로 갈지 정하는 규칙은 `when:` 칸에 적는다.
  when이 없으면 실패가 아니라 ⚠️(수용된 위험)로 남는다 — 원본 흐름도의 ◆ 문장을 옮겨 적으라는 뜻.
- **루프백**: `loop_to: <되돌아갈 스킬>` + `loop_exit: <반복이 끝나는 조건>`.
  next에 섞지 않는다 — 섞으면 순환 검사가 무의미해진다. 점검기는 세 가지를 본다:
  ① 대상이 실재하는가 ② 정말 '뒤로' 가는가(대상에서 next로 자신에게 돌아오는가)
  ③ 탈출 조건이 있는가 (없으면 ❌ 무한반복, `(미정)`이면 ⚠️).
- 루프백도 순서를 바꾸므로 ATF ④순서 가변성을 충족한다 — 산출물 유형이 「팀 에이전트(루프백 있음)」가 된다.
- **팀 흐름표**: 스킬 사이 연결의 운반책. `adapt_upstream.py`의 4번째 인자로 주면
  chain·halt_at·next·when·loop_to가 채워진다. 문법은 그 파일 상단 주석 참조.
  흐름표가 없으면 chain은 (미정)으로 남는다 — 지어내지 않는다.

## readchk — 읽은 바를 먼저 적고, 갈래는 하나만 앞세운다

paperthin `depth/readchk`를 도구에 옮긴 것이다. 목적은 **막지 않는 것** —
정해지지 않은 것이 있어도 팩은 돌아가고, 결정만 눈에 보이게 남는다.

```
python3 check/readchk.py <팩 경로>     # DECISIONS.md 생성
```

`DECISIONS.md`에 두 가지를 적는다:

1. **이해한 바** — 필드 나열이 아니라 문장으로 재진술한다("스킬 3개를 한 줄로 이었다: A → B → C").
   나중에 읽는 사람이 이 문서와 팩을 대조해 의도대로 만들어졌는지 감사할 수 있다.
2. **아직 정해지지 않은 것** — 여럿이어도 **가장 무거운 하나만** 앞세운다. 나머지는 순서대로 뒤에 적는다.

무게 순서: 검수 없음 → 기록자 충돌 → 임계값 상충 → 중간 정지 누락 → 데이터 미정 → 연동 미정.

### 수용된 위험 (⚠️) — 실패와 구분한다

검수 지점이 없을 때 두 경우를 다르게 다룬다.

| | 판정 | 뜻 |
|---|---|---|
| DECISIONS.md에 `결정됨` 기록 + 기획서에 위험 명시 | **⚠️ 수용된 위험** | 실패로 세지 않는다. 다만 출력에서 **사라지지 않는다** |
| 기록 없음 | **❌ 실패** | 모르고 빠뜨린 것으로 본다 |

모르고 빠뜨린 것과 알고 감수한 것은 다르다. 수용은 기록을 요구하므로 감사 가능하고,
"전체 통과"에도 `(수용된 위험 N건 ⚠️ — 사라지지 않습니다)`가 함께 찍힌다.

## 실행 방법

```
python3 check/check_contract.py <팩 경로> --run-check   # L0 게이트 → 통과 시 통합 점검기
python3 check/run_check.py <팩 경로>      # L1~L4 기계 판정
python3 check/simulate_run.py <팩 경로>     # 시나리오 E2E 실행 + 오류 주입
python3 check/run_check.py --self         # 저장소 자기 판정 (아래 SELF 레이어)
```

출력: 레이어별 PASS/FAIL과 실패 사유. 종료 코드 0 = 기계 판정 전체 통과.
기계 판정 통과 후 L4의 [사람 판정] 2개를 수동으로 수행해야 최종 성공이다.

## SELF 레이어 — 저장소 자신에게 적용하는 통합 점검기

L2("기획서가 모르는 스킬 = 반영 안 된 맥락")와 같은 논리를 이 저장소에 적용한다.
문서가 도구를 따라가지 못하는 드리프트를 기계가 잡는다.

- [ ] README 구조도가 실재하는 최상위 폴더를 전부 안내하는가
- [ ] prompts/·check/가 구조도에만 있지 않고 사용법 설명이 있는가

> 반대 방향(README에만 있고 실재하지 않는 폴더) 검사는 의도적으로 두지 않았다.
> 중첩 폴더 표기와 한국어 문장의 '/'를 최상위 폴더와 구별하지 못해 오탐만 냈다 — 제거 우선.

## 판정 철학 (paperthin)

- 점검기는 통과시키기 위해서가 아니라 **탈락시키기 위해** 존재한다 (egoless review).
- 검사 항목을 늘리기 전에, 그 항목이 실패를 실제로 잡아낸 적이 있는지 먼저 물어라 (제거 우선).
- 기계 판정이 통과해도 사람 판정 없이 "동작 확인"이라고 적지 않는다 (mandela — 자기 확인 금지).
