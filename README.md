# Activity Coach_SKI — 팀 AI 에이전트 패키징 도구 모음

**개인이 만든 스킬들을 하나의 팀 에이전트로 묶고, 제대로 묶였는지 검증하고, 그 결과를 발표 자료로 만드는 것**까지를 한 저장소에서 지원합니다.
SK이노베이션 AI Agent 제작 교육(세션 6·7)에서 쓰도록 만들어졌습니다.

> **이름의 뜻** — 교육의 코치 계열을 잇는 이름입니다.
> 세션 3 **핏 코치**(업무가 에이전트에 맞는가) → 세션 4 **Wireframe Coach**(태스크 하나를 어떻게 판단하는가)
> → 세션 4 **Merge Coach**(팀 것을 하나로) → 세션 6 **Activity Coach**(액티비티=Lv5를 팀 에이전트로 패키징).
> 각 코치가 한 계층을 맡고, Activity Coach가 마지막 통합 계층을 맡습니다.

이 저장소는 세 가지 도구로 이루어져 있습니다.

| 도구 | 무엇을 하나 | 언제 쓰나 | 폴더 |
|---|---|---|---|
| 🎤 **인터뷰 프롬프트** | 질문에 답하면 팀 에이전트 기획서가 나옴 | 스킬들을 팀 단위로 묶기 시작할 때 | [`prompts/`](prompts/) |
| ✅ **통합 점검기** | 상류 산출물을 팩으로 변환하고, 잘 묶였는지 판정하고, 실제로 돌려봄 | 패키징 전후 | [`check/`](check/) |
| 📊 **slide-pack** | 문서를 HTML 슬라이드로 변환 | 팀에 공유하거나 발표할 때 | 저장소 루트 |

> 처음이시라면 아래 "전체 흐름"만 읽으세요. 각 도구의 상세는 그 아래에 있습니다.

## 📦 설치 (교육생용 · 인터넷 없이)

사내망에서 GitHub에 붙지 않아도 됩니다. 폴더를 받아 복사만 하면 됩니다.

```bash
bash install.sh          # mac / Linux / WSL
```
```powershell
powershell -ExecutionPolicy Bypass -File install.ps1   # Windows
```

`~/.claude/skills/`에 스킬 2개(`activity-coach`, `slide-pack`)가 들어갑니다.
**외부 패키지가 필요 없습니다** — 전 스크립트가 파이썬 표준 라이브러리만 씁니다.

설치 스크립트는 마지막에 재무 샘플 팩을 실제로 점검해 보고 통과해야 완료로 알립니다.

자세한 것은 [INSTALL.md](INSTALL.md) — 첫 실습, 값 바꿔 보기, 자주 나오는 문제까지 있습니다.

## 🧭 전체 흐름 — 세션 6에서 7까지

```
들어오는 것 (둘 중 하나)
  · 개인이 각자 쓴 SKILL.md                    → ① 인터뷰로 채운다
  · 세션 3·4 코치 산출물 / 워크플로우 설계도 HTML → adapt_* 로 팩으로 변환
      │
      ├─① prompts/   확인표로 아는 것을 통째 확인, 빈 칸만 질문
      │               →  agent-plan.md (기획서 = 원본/SSOT) + CONTRACT.md (이름 계약)
      │
      ├─② check/     readchk      → DECISIONS.md (이해한 바 + 미결 갈래 하나)
      │               계약 게이트  → 🟢 통과 → 통합 점검기 → simulate_run 실제 실행
      │                             🟡 표기 어긋남 → 교정안 → 재검사
      │                             🔴 충돌 → 팀이 결정 → 재검사
      │
      └─③ slide-pack  발표 자료로 만든다        →  ...-deck.html (발표용 SK CI 테마)
```

각 단계는 앞 단계의 산출물을 그대로 입력으로 받습니다. 기획서 하나가 끝까지 따라갑니다.

**정해지지 않은 것이 있어도 멈추지 않습니다.** `readchk`가 미결을 `DECISIONS.md`에 적고
가장 무거운 것 하나만 앞세웁니다. 팀이 위험을 알고 수용하면 ⚠️로 통과하되 표시는 남습니다.

> **왜 게이트가 먼저인가**: 각자 만든 스킬은 표 이름·페이로드 이름이 서로 다릅니다.
> 그 상태로 점검기를 돌리면 실패가 쏟아질 뿐 아니라, 이름이 어긋난 탓에 **진짜 충돌이 가려집니다**
> (두 사람이 같은 표에 쓰는데 철자가 달라 다른 표로 보이는 등). 게이트가 이름을 정본으로 맞춘 뒤에
> 점검기가 구조를 봅니다.

## 📦 산출물 — 세션이 끝나면 손에 남는 것

팀 폴더 하나입니다. 아래는 실제 예시([`ax-share-agent`](examples/sample/ax-share-agent/))의 내용 그대로입니다.

```
팀-agent/
├── README.md          사용법 3줄 + 기획서 링크          (처음 여는 사람)
├── agent-plan.md      기획서 8절 — 이것이 원본(SSOT)    (사람 + 점검기)
├── AGENTS.md          역할 · 입출력 · 도구 · 트리거      (사람)
├── CONTRACT.md        표 · 기록자 · 순서 · 정지 지점     (점검기가 읽음)
├── DECISIONS.md       이해한 바 + 아직 안 정해진 것      (나중에 감사하는 사람)
├── skills/depth/*/SKILL.md   개인이 만든 스킬들          (AI)
├── data/*.csv         원본 데이터                        (AI)
└── run.py             실행기
```

돌리면 `out/`에 결과가 쌓입니다. 위 예시는 4개가 나옵니다 —
`공유대상자목록.csv` · `첨부파일목록.md` · `메일초안.md` · `발송대기.md`.
**마지막 단계가 사람고유라 발송은 일어나지 않습니다.** 실행기에 발송 코드 자체가 없습니다.

| 필수 파일 | 없으면 |
|---|---|
| `README.md` · `agent-plan.md` · `AGENTS.md` | L1 실패 |
| `CONTRACT.md` | 계약 게이트가 🔴로 멈추고 채울 서식을 보여줌 |
| `DECISIONS.md` | 없어도 됨. `readchk`가 만들어 줌 |

## ① 인터뷰 프롬프트 — 기획서 만들기

팀장이 AI 코치(이노허브/Codex)에 프롬프트를 붙여넣으면 AI가 팀에게 물어봅니다. 두 판이 있습니다:

| 판 | 방식 | 언제 |
|---|---|---|
| [**v2**](prompts/lv5-packaging-prompt-v2.md) (권장) | SKILL.md·와이어프레임을 먼저 읽어 **아는 것은 확인표로 통째 확인**, 빈 칸만 질문 | 와이어프레임이 있을 때 |
| [v1](prompts/lv5-packaging-prompt.md) | 6문항을 처음부터 전부 질문 | 와이어프레임 없이 스킬만 있을 때 |

v2는 판단기준·예외·환경 태그·실행 순서를 파일에서 자동으로 채웁니다(실측: 노드 13개분).
그만큼 앞단이 짧아져 동작 테스트에 15분을 확보합니다.

**묻는 것 6가지**: 우리 팀은 누구인가 → 스킬의 역할 → 쓰는 데이터(표·칸 이름까지) → 사용 시나리오 → 결과가 반영될 곳 → 다른 스킬과의 연동

**나오는 것**: `agent-plan.md` 기획서(8절) + 공용 드라이브에 올릴 폴더 트리 + 동작 테스트 체크리스트

프롬프트 문서에는 50분 세션 타임라인과, 파일 접근이 안 되는 채팅형 모델 환경에서 쓸 때의 주의사항 8가지도 함께 들어 있습니다.

## ② 통합 점검기 — 잘 묶였는지 검증하기

패키징한 폴더를 넣고 실행하면 통과/실패가 나옵니다. **계약 게이트부터 시작하세요.**

```bash
python3 check/check_contract.py examples/sample/team-agent --run-check  # 게이트 → 통과 시 통합 점검기
python3 check/simulate_run.py examples/sample/team-agent                  # 시나리오 처음부터 끝까지 실행
bash check/test_upstream_e2e.sh                                           # 상류 코치 산출물부터 전 구간
python3 check/readchk.py examples/sample/team-agent                       # 읽은 바 기록 + 미결 갈래 하나
python3 check/adapt_workflow.py <워크플로우.html> <출력 팩>                 # 설계도 HTML → 팩
```

**정해지지 않은 것이 있어도 막지 않습니다.** `readchk`가 `DECISIONS.md`에 "이해한 바"와
"아직 정해지지 않은 것"을 적고, 미결이 여럿이면 **가장 무거운 하나만** 앞세웁니다.
검수 지점이 없는 설계도 팀이 위험으로 수용하고 기록하면 ⚠️로 통과합니다 —
다만 그 표시는 출력에서 사라지지 않습니다.

**팀이 내린 결정은 덮어쓰지 않습니다.** `DECISIONS.md`에 `결정됨`이 적혀 있으면 `readchk`를
다시 돌려도 그 파일을 건드리지 않고, 새로 읽은 결과를 `DECISIONS.new.md`로 따로 씁니다.
(재실행이 기록을 지운 적이 있어 막아 둔 것입니다 — 결정을 남기려는 도구가 결정을 지우면 안 됩니다.)

**상류 코치 산출물에서 시작하기.** 세션 3(ATF 핏 코치)·세션 4(와이어프레임 코치)의 출력을
그대로 팩으로 변환합니다 — 참가자가 스킬을 새로 쓸 필요가 없습니다.

```bash
python3 check/adapt_upstream.py <와이어프레임 폴더> <ATF html> <출력 팩>
```

어댑터는 `WFDATA`의 판단기준·예외·환경태그를 skill.md로 옮기고, `atf-data`의 판정·6기준을
기획서로 옮깁니다. **상류에 없는 것은 지어내지 않고 `(미정)`으로 남깁니다** — 스킬 사이 순서,
표·칸 이름, 임계값이 여기 해당합니다(참가자는 각자 LV6 하나만 그리므로 연결 정보가 없습니다).
그 자리는 세션 6 인터뷰가 채웁니다. 예시는 [`examples/upstream/`](examples/upstream/).

게이트는 팀원들이 각자 만들어 온 스킬을 `CONTRACT.md`(표·기록자·체인·페이로드·임계값)와 대조해 세 갈래로 나눕니다:

| 판정 | 뜻 | 팀이 할 일 |
|---|---|---|
| 🟢 GREEN | 위반 없음 | 없음 — 점검기가 이어서 돕니다 |
| 🟡 YELLOW | 표기만 어긋남 (`견적_비교표` vs `견적비교표`) | `REMEDIATION.md`의 치환 제안을 확인·반영 후 재검사 |
| 🔴 RED | 팀 결정 필요 (기록자 중복, 임계값 상충 등) | 누가 쓸지·어느 값이 맞는지 정한 뒤 재검사 |

**무엇을 보는가** (상세는 [`check/통합점검-기준.md`](check/통합점검-기준.md)):

| 레이어 | 판정하는 것 |
|---|---|
| L1 구조 | 필수 파일이 있는가, 스킬마다 기계가 읽을 헤더가 있는가 |
| L2 맥락 반영 | 기획서가 모르는 스킬은 없는가, 명세 밖 데이터를 쓰지 않는가 |
| L3 충돌·일관성 | 한 표에 기록하는 스킬이 둘 이상은 아닌가, 스킬 체인이 끊기지 않는가, 용어·임계값이 문서마다 같은가 |
| L4 위임 | 시나리오 처음부터 끝까지 도는가, 끝점마다 사람 확인에서 멈추는가 |

판정은 세 가지입니다 — ✅ 통과 · ❌ 실패 · **⚠️ 수용된 위험**. 검수 지점이 없어도 팀이
`DECISIONS.md`에 결정을 기록하고 기획서에 위험을 명시했으면 ⚠️로 통과합니다. 기록이 없으면
❌입니다. **모르고 빠뜨린 것과 알고 감수한 것을 구분합니다.**

**어느 쪽이든 통과합니다 — 이름만 정확히 붙습니다.** 점검기는 두 가지를 보고 유형을 정합니다:

| 흐름 | 산출물 유형 | ATF 대응 |
|---|---|---|
| AI 태스크(자동+증강) 3개 미만 | `팀 스킬팩 (AI 태스크 N개 — ③다단계성 미충족)` | ③ 미충족 |
| 순서가 매번 같음 | `팀 스킬팩 (순차 실행)` | ④ 미충족 |
| 갈림길 있음 | `팀 에이전트 (갈림길 있음)` | ③④ 충족 |
| 되돌아감(루프백) 있음 | `팀 에이전트 (루프백 있음)` | ③④ 충족 |

직선이라고, 태스크가 적다고 탈락시키지 않습니다. 만든 스킬이 그대로 에이전트의 부품이 되기
때문입니다. 갈림길을 계약에 적을 때는 경로를 `;`로 나눠 적습니다: `chain: A -> B -> D; A -> C -> D`

### 갈림길과 루프백 — 원본 업무의 흐름 그대로

실제 업무는 갈라지고 **되돌아갑니다**(반려·재작업·재대사). 디자인캠프 Process Flow에는
분기(`◆ 조건?`)와 루프백(`↩`)이 글로 적혀 있는데, 와이어프레임 단계에서 사라집니다 —
참가자는 각자 자기 Lv6 하나만 그리기 때문입니다. 그래서 스킬 frontmatter에 세 칸을 둡니다:

| 칸 | 뜻 | 없으면 |
|---|---|---|
| `next: A \| B` | 갈림길 — 결과에 따라 다음이 갈린다 | — |
| `when:` | 어느 쪽으로 갈지 정하는 규칙 (원본의 ◆ 문장) | ⚠️ 수용된 위험 |
| `loop_to:` / `loop_exit:` | 되돌아갈 스킬 / 반복이 끝나는 조건 | 탈출 조건 없으면 ❌ (무한반복) |

루프백은 `next`에 섞지 않습니다 — 섞으면 순환 검사가 무의미해집니다. 점검기는 세 가지를 봅니다:
① 대상이 실재하는가 ② 정말 '뒤로' 가는가 ③ 탈출 조건이 있는가.

**팀 흐름표**: 스킬 사이 연결의 운반책입니다. 와이어프레임에는 없는 정보라
사람이 옮겨 적어야 합니다.

```
스킬A -> 스킬B              앞으로 잇기
스킬A -> 스킬B | 스킬C      갈림길
스킬A ? <조건 문장>          갈림길 조건
스킬A ↩ 스킬B (탈출: 조건)   루프백
```

```bash
python3 check/adapt_upstream.py <와이어프레임 폴더> <ATF html> <출력 팩> [팀흐름표.md]
```

흐름표를 주면 `chain`·`halt_at`·`next`·`when`·`loop_to`가 채워지고, 안 주면 `(미정)`으로
남습니다 — 지어내지 않습니다. 예시: [`examples/upstream/정세브리핑-팀흐름표.md`](examples/upstream/정세브리핑-팀흐름표.md)

판정에 쓰이는 `human: 자동|증강|사람고유` 필드는 스킬 frontmatter에 들어갑니다. 없으면
태스크 수 판정을 건너뜁니다.

**중요**: 자동 판정이 전부 통과해도 그것만으로 "동작 확인"이라고 적지 마세요. 실제 환경에서 시나리오를 한 번 돌리고, 틀린 입력(미승인 건, 임계값 초과)을 일부러 넣어 정말 멈추는지 확인해야 끝입니다.

**예시로 확인하기**: [`examples/sample/team-agent/`](examples/sample/team-agent/)에 5개 스킬로 이루어진 완성 팩이 있습니다. 위 명령을 그대로 실행하면 통과하는 것을 볼 수 있고, `out/` 폴더에 실행 결과(품의초안·재요청초안·확인브리핑)가 들어 있습니다.

**갈림길이 있는 예시**: [`examples/sample/medical-expense-agent/`](examples/sample/medical-expense-agent/) —
SKI AX 과제 「의료비 판독 AI」(Talent AX실·HR AI)를 그대로 옮긴 팩입니다.
`run.py`를 돌리면 청구 11건이 「지급기준대조」에서 **세 갈래로 갈라져** 서로 다른 파일로 떨어지고,
사람고유 지점에서 멈춥니다. `agent-mockup.html`이 그 실행 장면을 화면으로 보여줍니다.

**루프백이 있는 예시**: [`examples/sample/quarterly-close-agent/`](examples/sample/quarterly-close-agent/) —
AX전략 워크샵 **재무본부 회계관리팀**의 실제 산출물(Agent 1~4)에서 옮긴 팩입니다.
원본 Agent 3이 결산 지연의 주요 원인으로 지목한 **루프백 L4(차이대사)** 를 그대로 담았습니다.
`run.py`를 돌리면 1회차에 차이가 나 사람에게 갔다가 되돌아와, 2회차에 차이 0으로 루프를 빠져나갑니다.

## ③ slide-pack — 문서를 슬라이드로

마크다운 문서를 넣으면 브라우저에서 바로 열리는 슬라이드 덱(HTML 파일 1개)이 나옵니다.

- 파워포인트가 필요 없습니다. 더블클릭하면 바로 발표 화면이 뜹니다.
- 파일 하나가 전부라 드라이브·메일로 그냥 전달하면 됩니다. 인터넷이 없어도 열립니다.
- 넘기기: **← → 방향키, 스페이스바, 화면 클릭**

### 3분 만에 시작하기

**1단계.** 슬라이드로 만들 문서를 준비합니다. (예: 위에서 만든 `agent-plan.md`)

**2단계.** AI 코치에게 이 저장소 폴더를 열어둔 상태로 말합니다:

```
agent-plan.md를 slide-pack으로 슬라이드 덱 만들어줘
```

**3단계.** 원문과 같은 폴더에 `agent-plan-deck.html`이 생깁니다. 더블클릭해서 열어보세요.

> 💡 결과를 미리 보려면 [`examples/sample/`](examples/sample/)에 입력(`agent-plan.md`)과 출력(`agent-plan-deck.html`) 쌍이 있습니다.

### 테마는 2가지 — 언제 무엇을 쓰나요?

| | 기본 테마 (다크) | SK CI 테마 (라이트) |
|---|---|---|
| **생김새** | 어두운 배경, 차분한 톤 | 흰 배경 + SK 레드/오렌지 포인트 |
| **언제** | 팀 내부에서 빠르게 훑을 때 | 발표·보고 등 남에게 보여줄 때 |
| **예시** | [`examples/lv5-packaging-deck.html`](examples/lv5-packaging-deck.html) | [`examples/lv5-presentation-deck-sk.html`](examples/lv5-presentation-deck-sk.html) |
| **호출** | 그냥 요청하면 기본 적용 | 아래 문장으로 요청 |

SK CI 테마로 만들려면:

```
agent-plan.md를 slide-pack SK CI 테마로 발표용 덱 만들어줘.
DESIGN.md의 토큰만 사용하고, template-sk-ci.html 스켈레톤을 써.
```

발표용으로 만들면 세 가지가 추가됩니다:

1. **제목이 주장이 됩니다** — "데이터 구조" 대신 "사람은 검증 지점에서만 개입한다"처럼 청중이 기억할 한 문장으로.
2. **섹션 구분 슬라이드** — 3부 이상이면 빨간 배경의 파트 전환 슬라이드가 들어갑니다.
3. **역할 분담과 원문 안내** — 첫 장에 발표/데모/Q&A 담당, 마지막 장에 원문 위치.

### 문서 종류별 추천

| 넣는 문서 | 추천 테마 | 이렇게 나옵니다 |
|---|---|---|
| 에이전트 기획서 | 발표용(SK CI) | 문제 → 해결 → 데모 → 배운 것, 4부 구성 |
| 교육 자료·프롬프트 | 기본(다크) | 섹션당 1장, 표 중심 요약 |
| 체크리스트·테스트 결과 | 기본(다크) | 항목별 불릿, 결과 ✅/❌ |
| 데모 시나리오 대본 | 발표용(SK CI) | "라이브 데모" 구분 슬라이드 중심 |

## 🏢 회사 색(CI)을 바꾸고 싶다면

색과 폰트의 **원본은 `DESIGN.md` 한 파일**입니다. 슬라이드 파일을 직접 고치지 마세요.

1. 사내 브랜드 가이드라인에서 공식 색상값(hex)을 확인합니다.
2. `DESIGN.md`의 **"2. 컬러 팔레트" 표의 값만** 바꿉니다.
3. `assets/template-sk-ci.html` 상단 `:root`의 같은 토큰에 반영합니다.
4. 이후 만드는 덱에 자동 적용됩니다. 이미 만든 덱은 다시 생성하세요.

> 현재 SK 레드(#EA002C)·오렌지(#F47725)는 공개 자료 기반 근사치입니다. 공식 값을 확보하면 위 절차대로 교체하세요.

## ✅ 슬라이드가 잘 만들어졌는지 확인하는 법

AI에게 "검증해줘"라고 하면 자동으로 점검합니다.

- [ ] 외부 인터넷 요청이 0건인가 (오프라인에서도 열리는가)
- [ ] 슬라이드가 10장 이하인가
- [ ] 슬라이드당 불릿 5개·표 6행을 넘지 않는가
- [ ] 마지막 슬라이드에 원문 위치가 적혀 있는가
- [ ] 파일 이름이 `원문이름-deck.html` 규칙을 따르는가

## ❓ 자주 묻는 질문

**Q. 슬라이드 내용을 조금 고치고 싶어요. HTML을 직접 수정해도 되나요?**
안 됩니다. 슬라이드는 요약본이고 **원문 문서가 원본(SSOT)** 입니다. 원문을 고친 뒤 "덱 다시 만들어줘"라고 하세요. HTML을 직접 고치면 다음 재생성 때 사라집니다.

**Q. 점검기가 통과하면 우리 에이전트는 완성된 건가요?**
아닙니다. 자동 판정은 구조와 일관성만 봅니다. 실제 환경에서 시나리오를 한 번 돌려보고, 일부러 틀린 입력을 넣어 멈추는지까지 확인해야 완성입니다.

**Q. 10장이 넘는 긴 문서는요?**
스킬이 병합·요약해 10장 안으로 줄이고, 뺀 내용은 마지막 슬라이드의 "원문에서 확인" 안내로 대신합니다. 줄이기 싫다면 문서를 나눠 덱을 두 개 만드세요.

**Q. 회사 로고를 넣고 싶어요.**
현재는 넣지 않는 것이 규칙입니다(파일 자기완결 원칙 + 상표 관리). 필요하면 `DESIGN.md`의 가드레일을 먼저 수정하세요.

**Q. 파워포인트(pptx)로 변환할 수 있나요?**
산출물은 HTML입니다. 발표는 브라우저 전체화면(F11)으로 충분합니다. pptx가 꼭 필요하면 AI에게 별도로 요청하세요.

**Q. 인쇄하거나 PDF로 저장하려면?**
브라우저에서 열고 인쇄(Ctrl+P) → "PDF로 저장". 슬라이드를 한 장씩 넘기며 저장하는 것이 가장 깔끔합니다.
