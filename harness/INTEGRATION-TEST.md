# 통합 패키징 테스트 하네스 (Lv.5 Integration Harness)

**목적**: 개인 Lv.6 스킬들이 하나의 팀 Lv.5 에이전트로 "잘" 통합되었는지 판정한다.

**성공 조건** (사용자 정의 그대로):
> 기존 스킬의 맥락이 충분히 반영되면서도, 맥락 충돌과 일관성이 깨지지 않고,
> 하나의 일을 처음부터 끝까지 위임할 수 있는 에이전트로 통합되어야 한다.

이를 4개 검증 레이어로 분해한다. L1~L3은 스크립트(`run_harness.py`)가 기계적으로 판정하고,
L4의 일부는 사람(또는 AI 리뷰어)이 시나리오를 실제 실행해 판정한다.

## 검증 레이어

### L1. 구조 (패키징이 규격을 지키는가)
- [ ] 필수 파일 존재: README.md, agent-plan.md, AGENT.md, skills/, data/
- [ ] 각 skill.md에 기계가 읽을 헤더(frontmatter)가 있는가: name, inputs, outputs, reads, writes, next
- [ ] agent-plan.md가 팩 안에 하나만 존재하는가 (SSOT 유일성)

### L2. 맥락 반영 (기존 스킬의 맥락이 살아있는가)
- [ ] 모든 스킬이 agent-plan.md에 언급되는가 (기획서가 모르는 스킬 = 반영 안 된 맥락)
- [ ] 각 스킬이 읽고/쓰는 표가 전부 기획서 3절 데이터 명세에 있는가 (명세 밖 데이터 = 누락된 맥락)
- [ ] 스킬 본문이 비어있지 않은가 (헤더만 있는 스킬 = 맥락 소실)

### L3. 맥락 충돌·일관성 (합쳤을 때 서로 싸우지 않는가)
- [ ] **단일 기록자**: 같은 표에 쓰는(writes) 스킬이 2개 이상이면 실패 — 기록 주체는 표당 하나
- [ ] **흐름 정합**: 시작점 1개, 모든 스킬에 도달(고아 없음), 순환 없음, next가 실재하는
      스킬을 가리키는가, 앞 스킬의 outputs와 뒤 스킬의 inputs가 이름까지 일치하는가
      (갈림길은 허용한다 — 위 '산출물 유형' 참조)
- [ ] **용어 일관**: 표 이름 문자열이 파일마다 다르게 쓰이지 않는가 (예: 견적비교표 vs 견적_비교표)
- [ ] **규칙 일관**: 휴먼인더루프 임계값(예: ±15%)이 AGENT.md·기획서·스킬에서 같은 값인가

### L4. 처음부터 끝까지 위임 (End-to-End)
- [ ] 체인의 시작 입력 = 기획서 4절 시나리오의 입력, 체인의 끝 출력 = 시나리오의 산출물
- [ ] 마지막 단계가 자동 발송하지 않고 휴먼인더루프에서 멈추는가 (기계 판정: 최종 스킬 writes 없음 + 확인 요청 명시)
- [ ] **[사람 판정]** 시나리오를 실제로 한 번 실행: 트리거부터 산출물까지 사람 개입이
      선언된 휴먼인더루프 지점 외에 없었는가
- [ ] **[사람 판정]** 틀린 입력(미승인 공급사, ±15% 초과 단가)을 넣었을 때 실제로 멈추는가

## L0 — 계약 준수 게이트 (하네스보다 먼저)

팀원이 **각자 자유롭게 만들어 온** 스킬은 표 이름·페이로드 이름·임계값이 서로 어긋난다.
그 상태로 하네스를 돌리면 실패가 쏟아질 뿐 아니라, **이름이 어긋난 탓에 진짜 충돌이 가려진다.**

실측 예: 두 사람이 같은 표에 기록하는데 한 명은 `견적비교표.xlsx`, 다른 명은 `견적_비교표.xlsx`로
적으면 하네스의 단일 기록자 검사가 서로 다른 표로 보고 **통과시킨다**. 임계값도 한 명이 "20% 넘게",
다른 명이 "±15%"로 적으면 형식이 달라 검사에 걸리지 않는다.

그래서 하네스 앞에 계약 준수 게이트를 둔다. 게이트가 정본 이름을 보장하므로,
하네스는 "이름은 이미 맞다"는 전제 위에서 구조와 일관성만 보면 된다.

```
python3 harness/check_contract.py <팩 경로> [--run-harness]
```

`CONTRACT.md`의 ```contract 블록(표·기록자·체인·페이로드·임계값·정지 지점)과 대조해 세 갈래로 분기한다.

| 판정 | 뜻 | 처리 |
|---|---|---|
| 🟢 GREEN (0) | 위반 없음 | `--run-harness`를 주면 곧바로 하네스 실행 |
| 🟡 YELLOW (1) | 표기 변형뿐 (`견적_비교표` vs `견적비교표`) | `REMEDIATION.md`에 치환 제안 → 사람이 확인·반영 후 재검사 |
| 🔴 RED (2) | 팀 결정이 필요 (기록자 중복, 계약에 없는 표·이름, 임계값 상충, 체인 밖 스킬) | 자동 교정하지 않음. 팀이 계약이나 담당을 정하고 재검사 |

RED가 하나라도 있으면 YELLOW 교정안을 만들지 않는다 — 이름부터 고쳐도 소용없기 때문(제거 우선).

## 실행 방법

```
python3 harness/check_contract.py <팩 경로> --run-harness   # L0 게이트 → 통과 시 하네스
python3 harness/run_harness.py <팩 경로>      # L1~L4 기계 판정
python3 harness/simulate_run.py <팩 경로>     # 시나리오 E2E 실행 + 오류 주입
python3 harness/run_harness.py --self         # 저장소 자기 판정 (아래 SELF 레이어)
```

출력: 레이어별 PASS/FAIL과 실패 사유. 종료 코드 0 = 기계 판정 전체 통과.
기계 판정 통과 후 L4의 [사람 판정] 2개를 수동으로 수행해야 최종 성공이다.

## SELF 레이어 — 저장소 자신에게 적용하는 하네스

L2("기획서가 모르는 스킬 = 반영 안 된 맥락")와 같은 논리를 이 저장소에 적용한다.
문서가 도구를 따라가지 못하는 드리프트를 기계가 잡는다.

- [ ] README 구조도가 실재하는 최상위 폴더를 전부 안내하는가
- [ ] prompts/·harness/가 구조도에만 있지 않고 사용법 설명이 있는가

> 반대 방향(README에만 있고 실재하지 않는 폴더) 검사는 의도적으로 두지 않았다.
> 중첩 폴더 표기와 한국어 문장의 '/'를 최상위 폴더와 구별하지 못해 오탐만 냈다 — 제거 우선.

## 판정 철학 (paperthin)

- 하네스는 통과시키기 위해서가 아니라 **탈락시키기 위해** 존재한다 (egoless review).
- 검사 항목을 늘리기 전에, 그 항목이 실패를 실제로 잡아낸 적이 있는지 먼저 물어라 (제거 우선).
- 기계 판정이 통과해도 사람 판정 없이 "동작 확인"이라고 적지 않는다 (mandela — 자기 확인 금지).
