```
## 상황
- 우리 팀은 팀장 1명 + 팀원 2명으로 구성되어 있고, 각자 Lv.6 스킬(skill.md)을 1개씩 만들었다.
- 이 개인 스킬들을 공용 드라이브에서 하나의 팀 Lv.5 에이전트로 통합·패키징하려고 한다.
- 이 폴더의 스킬 파일(skill.md)들을 먼저 모두 읽어라. 각 스킬이 무엇을 하는지 한 줄씩 요약해서 보여준 뒤 인터뷰를 시작하라.

## 설계 철학 (paperthin 원칙 — 인터뷰와 기획서 작성 내내 지켜라)
1. **제거 우선(Removal-first)**: 스킬을 합칠 때 기능을 추가하지 말고, 중복·소음·모호함을 먼저 제거하라.
   두 스킬이 같은 일을 하면 하나로 합치고, 아무도 답하지 못하는 항목은 기획서에서 빼라.
2. **단일 진실 원천(SSOT)**: 팀의 데이터(표·파일)는 반드시 한 곳에만 원본을 두고,
   다른 곳에서는 참조만 하게 하라. 같은 정보가 두 파일에 있으면 어디가 원본인지 반드시 확정하라.
3. **패치가 아닌 재작성(re0)**: 개인 스킬 3개를 이어붙이지 말고,
   팀 에이전트 관점에서 깨끗한 v0으로 다시 구조화하라.
4. **경계 명시(Bounded scope)**: 에이전트가 자동으로 해도 되는 일과
   반드시 사람이 확인해야 하는 일(휴먼인더루프)을 처음부터 구분해서 명시하라.
5. **다관점 검증(Egoless review)**: 각 답변에 대해 스킬을 만들지 않은 다른 팀원의 눈으로
   "이게 정말 맞나?"를 한 번씩 되물어라.

## 인터뷰 규칙
- 한 번에 반드시 한 질문만 한다.
- 모든 질문은 객관식(A/B/C/D)으로 제시하고, 마지막에 "E. 기타(직접 입력)"를 항상 포함한다.
- 선택지는 방금 읽은 skill.md의 실제 내용을 근거로 구체적으로 만들어라. 일반론 선택지를 만들지 마라.
- 답변이 모호하면 다음 질문으로 넘어가지 말고 한 번 더 좁혀서 물어라.
- 답을 받을 때마다 "지금까지 확정된 내용"을 3줄 이내로 요약해서 보여준 뒤 다음 질문으로 넘어가라.

## 인터뷰 질문 (이 순서대로 6개)
1. **팀 정체성**: 우리는 어떤 팀이고, 무엇을 위해 이 스킬과 에이전트를 쓰는가?
   (팀의 미션과 이 에이전트가 줄여줄 반복 업무를 확정)
2. **스킬의 역할**: 통합된 팀 스킬은 어떤 역할을 하는가?
   (읽은 skill.md들을 근거로, 겹치는 기능은 제거하고 핵심 역할 1문장으로 확정)
3. **데이터 정의**: 스킬은 팀의 어떤 데이터를 참조하고 저장하는가?
   — 표(파일) 이름과 칸(컬럼) 이름까지 구체적으로. 각 데이터의 원본 위치(SSOT)를 반드시 지정하라.
4. **사용 시나리오 1개**: 누가, 언제, 어떻게, 무엇을 위해 이 스킬을 사용하는가?
   (트리거 → 입력 → 처리 → 출력의 흐름으로 확정)
5. **결과물 반영**: 스킬의 결과물은 팀의 어떤 데이터(표·칸)에 어떻게 반영되어야 하는가?
   (3번에서 정한 표·칸과 반드시 연결. 새 표가 필요하면 그 이유를 물어라)
6. **연동성**: 이 스킬이 팀의 다른 스킬/에이전트와 연동될 수 있는가?
   (연동 지점이 있다면 주고받는 데이터 형식까지, 없다면 "현재는 독립"으로 확정)

## 인터뷰 종료 후 산출물: 팀 에이전트 기획서
6개 질문이 모두 확정되면, 아래 구조의 「팀 에이전트 기획서」를 마크다운 파일(agent-plan.md)로 작성하라.

# [팀 이름] Lv.5 에이전트 기획서
1. 팀과 목적 (질문 1)
2. 에이전트 역할 정의 (질문 2) — 한 문장 + 하는 일 / 하지 않는 일
3. 데이터 명세 (질문 3) — 표 이름 · 칸 이름 · 원본 위치(SSOT) · 읽기/쓰기 구분 표
4. 대표 시나리오 (질문 4) — 트리거 → 입력 → 처리 → 출력 흐름도
5. 결과물 반영 규칙 (질문 5) — 어떤 결과가 어떤 표의 어떤 칸에 기록되는가
6. 연동 맵 (질문 6) — 다른 스킬/에이전트와의 인터페이스
7. 검증·휴먼인더루프 지점 — 사람이 반드시 확인하는 단계(원칙 4에서 정한 경계)와 그 이유
8. 폴더 트리 — 공용 드라이브의 패키징 구조 (아래 규칙 적용)

## 패키징 폴더 트리 규칙 (paperthin의 사분면 구조 적용)
공용 드라이브에 다음 구조로 패키징하라:

팀이름-agent/
├── README.md          ← 사용법 3줄 + agent-plan.md로의 링크만 (내용을 복사하지 마라. 원본은 기획서 하나다)
├── agent-plan.md      ← 이 인터뷰로 만든 기획서 (SSOT — 에이전트 정보의 유일한 원본)
├── AGENTS.md           ← 에이전트 페르소나·행동 규칙
├── skills/
│   ├── depth/         ← 단독으로 한 번에 끝나는 스킬
│   ├── breadth/       ← 여러 파일·표를 가로지르는 스킬
│   └── coil/          ← 반복 주기마다 도는 스킬
└── data/              ← 참조·저장하는 표(SSOT 원본만)

각 개인 Lv.6 스킬을 성격에 맞는 사분면 폴더에 배치하고, 그 이유를 한 줄씩 적어라.
paperthin의 네 번째 사분면 mesh/(다관점 검증)는 폴더로 만들지 않는다 —
3인 팀에서는 별도 스킬이 아니라 동작 테스트의 상호 검증 절차와 세션 7의 팀 간 피드백으로 수행하기 때문이다(제거 우선).

## 마지막 단계: 동작 테스트 체크리스트
기획서 작성 후, 다음 체크리스트를 출력하고 팀과 함께 테스트를 진행하라:
- [ ] 팀원 각자가 드라이브에서 동일한 폴더를 마운트해서 같은 파일이 보이는가
- [ ] 질문 4의 시나리오를 처음부터 끝까지 실제로 실행했는가
- [ ] 결과물이 질문 5에서 정한 표·칸에 실제로 기록되었는가
- [ ] 프로세스 중간의 검증 지점에서 결과가 올바른지 사람이 확인했는가 (틀린 결과를 넣어 통과되는지도 시험)
- [ ] 휴먼인더루프 지점(원칙 4)에서 에이전트가 실제로 멈추고 사람에게 확인을 요청하는가
- [ ] 스킬을 만들지 않은 팀원이 README만 보고 사용할 수 있는가 (Egoless review)

지금 이 폴더의 skill.md 파일들을 읽고, 요약을 보여준 뒤 첫 번째 질문부터 시작하라.
```

## 다른 모델 환경에서 구동할 때 (예: ChatGPT Luna) — 예상 문제와 대비책

이 프롬프트는 이노허브(Codex)의 파일 시스템·드라이브 마운트를 전제로 작성되었습니다.
paperthin의 modelchk 원칙(특정 도구에 묶인 가정을 점검)에 따라, 파일 접근이 없는
일반 채팅형 환경에서 구동할 때 생길 수 있는 문제와 대비책입니다.

| # | 예상 문제 | 증상 | 대비책 |
|---|---|---|---|
| 1 | **폴더·파일 접근 불가** | "이 폴더의 skill.md를 읽어라"를 수행하지 못하거나, 읽은 척 내용을 지어냄(환각) | 프롬프트 붙여넣기 직후 skill.md 3개 전문을 직접 첨부하거나 본문에 붙여넣고, "첨부한 내용만 근거로 하라. 없는 내용은 '모름'이라고 답하라"를 추가 |
| 2 | **파일 산출 불가** | agent-plan.md를 파일로 저장하지 못하고 채팅 텍스트로만 출력 | 출력된 기획서를 사람이 공용 드라이브에 직접 저장. 저장 위치를 한 곳으로 정하지 않으면 SSOT가 깨지므로, 저장 담당자 1명(팀장)을 지정 |
| 3 | **마운트 검증 불가** | 체크리스트 1번(전원 동일 폴더 마운트)을 AI가 확인할 수 없음 | 이 항목은 AI 밖에서 사람이 수행하는 항목으로 전환 — 팀원 각자가 드라이브 화면을 열어 구두로 확인 |
| 4 | **인터뷰 규칙 드리프트** | 모델에 따라 "한 번에 한 질문" 규칙을 잊고 여러 질문을 한꺼번에 쏟아내거나, 확정 요약을 생략 | 규칙 위반 시 "규칙: 한 질문씩. 방금 답만 요약하고 다음 질문 하나만 해"라고 즉시 교정. 질문 2개가 넘어가면 진행자가 끊는다 |
| 5 | **컨텍스트 한도 초과** | 긴 인터뷰 끝에 앞에서 확정한 내용(질문 1~3)을 잊거나 다르게 말함 | 질문마다 나오는 "확정 요약"을 별도 문서에 복사해 두고, 기획서 작성 직전 6개 요약 전체를 다시 붙여넣어 재확인 |
| 6 | **세션 휘발** | 대화가 끊기면 인터뷰 진행 상태가 사라짐 | 5번과 동일 — 확정 요약 사본이 있으면 새 세션에서 "여기까지 확정됨" 붙여넣기로 이어서 진행 가능 |
| 7 | **실제 동작 테스트 불가** | m365 MCP·표 기록 연동이 없어 "결과물이 표에 기록되는가"를 실행이 아닌 말로만 검증(mandela가 경고하는 자기 확인) | 채팅 환경에서는 시나리오 시뮬레이션까지만 하고, 실제 기록 테스트는 이노허브로 돌아와 수행. 시뮬레이션 통과를 "동작 확인"으로 기획서에 적지 않는다 |
| 8 | **사내 데이터 유출** | 팀의 표 이름·칸 이름·업무 내용을 사외 서비스에 입력하게 됨 | 사외 모델 사용 전 회사 보안 규정 확인. 필요하면 표·칸 이름을 가명으로 치환해 인터뷰하고, 기획서 저장 시 실명으로 복원 |

**요약**: 인터뷰(질문 1~6)와 기획서 초안 작성은 어떤 모델에서도 가능하지만,
파일 읽기(시작 단계)·패키징·동작 테스트(마지막 단계)는 파일 시스템이 있는 이노허브에서만 실제로 검증됩니다.
다른 환경에서는 "설계까지만" 하고, 검증은 반드시 실행 가능한 환경에서 하세요.

**팁**
- 질문 3(데이터 정의)에서 시간이 가장 많이 걸립니다. 표·칸 이름이 바로 안 나오면 "지금 팀에서 실제로 쓰는 엑셀/시트 이름"부터 말하게 하세요.
- 인터뷰 중 의견이 갈리면 paperthin 원칙대로 "빼는 쪽"을 기본값으로 선택하세요. 나중에 추가하는 것이 잘못 넣은 것을 빼는 것보다 쉽습니다.
